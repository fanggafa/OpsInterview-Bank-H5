# 选择题编写规范（批量补题用）

## 本批口径（重要，先读这段）

用户要求：**「所有类目都补充 45 题，简单 20，中等 15，困难 10」**。

`20 + 15 + 10 = 45`，所以这三项是**新增题目内部的难度配比**，
而不是「该分类最终达到 45 道选择题」。

即：**每个分类新增 45 道选择题**，其中

| 难度 | 新增数量 |
|---|---|
| 简单 | 20 |
| 中等 | 15 |
| 困难 | 10 |
| 合计 | 45 |

23 个分类 × 45 = **1035 道**新增题。

> 已经核对过编号段容量：23 个分类全部能放下 45 个连续 id，不会溢出。

## 文件格式

每组题写成**独立 JSON 数组文件**，放在 `scripts/` 下，例如
`scripts/batch-choice-a.json`。合并脚本 `scripts/merge-batch.mjs` 会自动按 id 去重、
校验分类与编号段、排序后写回主库。

**不要直接改 `public/data/questions.json`。**

## 单题结构

```json
{
  "id": 1234,
  "type": "single",
  "category": "Nginx",
  "difficulty": "简单",
  "question": "……？",
  "options": [
    { "key": "A", "text": "……" },
    { "key": "B", "text": "……" },
    { "key": "C", "text": "……" },
    { "key": "D", "text": "……" }
  ],
  "answer": ["B"],
  "explanation": "……结构化解析……",
  "tags": ["location", "匹配优先级"],
  "frequency": "高频"
}
```

`type` 只能是 `single`（单选）或 `multiple`（多选）。**本次全部写单选**，
多选题另行处理。

## 硬性校验规则（`npm run validate:data` 会拦）

| 规则 | 说明 |
|---|---|
| id | 必须在你分到的编号段内，且不与现有题目重复 |
| category | 必须与分派给你的分类**完全一致**（含斜杠，如 `iptables/firewalld`） |
| difficulty | 只能是 `简单` / `中等` / `困难` |
| frequency | 只能是 `低频` / `中频` / `高频` |
| question | 非空，**不超过 60 字** |
| options | **2–6 项**，`key` 必须是从 A 起的连续大写字母（A/B/C/D），`text` 非空 |
| answer | key 数组，如 `["B"]`；不能为空、不能重复、必须都在 options 的 key 里 |
| explanation | **必填**，且 ≥ 10 字；建议 60–200 字 |
| tags | 2–5 个，不重复 |
| 字段白名单 | 只能有上面这些字段，多一个字段都会报错 |

## 内容质量要求（本次重点）

用户明确反馈「一些题目的答案过于简洁了」，所以 `explanation` 要写成**能学到东西**的解析，
不要只写一句「因为 X 所以 B」。

每个解析尽量覆盖这几点（按题型取舍，不必全占）：

1. **为什么对**：正确选项背后的机制/原理，一句话点到本质。
2. **为什么错**：至少点出 1–2 个干扰项错在哪（常见误区最容易考）。
3. **排查思路 / 链路**：如果是故障类题，给出「先看什么 → 再看什么」的顺序，
   以及关键命令（如 `iostat -x 1`、`ss -s`、`kubectl describe pod`）。
4. **案例/场景**：一句具体的现场描述（如「某次大促后 502 突增，最后发现是
   upstream keepalive 未开」），让知识落地。
5. **易混点**：与相邻概念的区别（如 502 vs 504、SYN 队列 vs accept 队列）。

解析里可以用这些排版语法（渲染层支持）：
- `**加粗**` 强调结论
- `` `行内代码` `` 包命令与配置项
- `- ` 列表
- `1. ` 有序列表（排查步骤很适合）
- Markdown 表格（对照类很适合）
- ` ```bash ` 代码围栏（写命令示例）

**注意**：代码围栏必须成对闭合，否则后面的正文会被吞进代码块（校验会拦）。

## 题目设计要求

- **题干要具体**，不要「以下关于 X 说法正确的是」这种泛题；
  写成「某台机器 X 现象，最可能的原因 / 下一步查什么」这种能考的形态。
- **干扰项要像真的**：把常见误区写成选项（例如把 `SYN 队列` 与 `accept 队列` 混起来），
  而不是凑四个明显错的。
- **难度分布**：按分派给你的数量写，`简单` 考单个命令/概念，
  `中等` 考机制与辨析，`困难` 考多步排查链路或组合场景。
- **不要与现有题目重复**：写之前先搜一下该分类已有题目的题干关键词
  （`grep` `public/data/questions.json`）。
- **不要跨分类串味**：Nginx 的题不要写成 MySQL 的内容。

## 交付前自检

```bash
# 只校验你会改到的文件，先确认 JSON 本身能解析
node -e "console.log(require('./scripts/你的文件.json').length)"

# 业务校验（会连带检查全库，必须全绿）
npm run validate:data
```

不要跑 `git` 命令，不要修改 `public/data/questions.json`，也不要合并——
合并由主代理统一执行。
